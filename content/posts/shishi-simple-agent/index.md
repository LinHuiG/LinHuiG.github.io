这次，我把拾事做成了一个小 Agent，让它在事项生成后，先通过工具查一查相关数据，为后续判断和处理补充依据。

这些查询当然也可以交给 Codex 这样的通用 Agent。查询数据库、读取配置，再根据结果分析问题，它们都有能力做。我没有打算再做一个通用 Agent，只是觉得，为了几次固定查询，就启用一个完整的 Agent，有些重。对于这种频繁发生、范围又相对固定的任务，我不太愿意把 token 花在额外的上下文和执行流程上。

我的选择是自己准备工具，让大模型直接选择和调用，由拾事负责执行与回传。通用能力上，这套小循环远不如成熟的 Agent；把范围收窄到事项依据的补充后，我希望能让调用过程更短一些，成本和日常使用效率也更适合这个场景。

真正需要解决问题时，我仍然通过“AI 一键处置”调用 Codex、DSH 这些通用 Agent，由它们完成后续调查和处理。这个小循环做的是处置前的资料准备，让事项先带上更多依据。

上一篇[《拾事的 AI 上下文工程》](https://blog.linhui.fun/posts/shishi-ai-context-engineering/)写了消息过滤、增量分析、按需检索和分层记忆，主要是在准备模型的输入。这一轮，拾事（ShiShi，下面简称 SS）补上了一层工具循环：模型选择工具，SS 执行，把实际结果交回模型，再把相关发现补充到事项依据里。

## 为什么要提前补充事项依据

测试同学发来一句：“这个功能怎么又不行了？”

这条反馈已经生成了一个需要跟进的事项。原因可能在代码，也可能只是数据不对，或者某个配置项没有打开。聊天记录能说明问题的现象，却未必包含判断原因所需的信息。相关记录存不存在，当前状态是什么，Apollo 里的配置值是否符合预期，往往还得另外查。

我希望事项生成以后，AI 能围绕这个事项，提前完成其中一部分固定查询。假设已经注册了查询数据库和读取 Apollo 配置的工具，它可以根据事项及关联消息中的线索取回数据，再把查到的情况补充进去。这样，我看到事项时就能多一些依据，也更容易判断该从哪里继续处理。

这些查询适合在正式处置前完成。等我准备处理这个问题时，相关数据和配置已经有了一份可参考的查询结果，后续调查便有了起点。

当然，一次查询通常不能说明全部原因。没有查到记录，可能是数据缺失，也可能是查询条件不完整；配置值看起来正常，也不能据此认定功能没有问题。补充依据时，需要区分查到了什么、据此推测了什么，以及还有什么没有确认。

## 核心就是一个工具循环

受到 Claude Code 的启发，我把这部分数据补充组织成了一个简单的循环：调用模型，执行模型选择的工具，把实际结果放回上下文，再调用模型。

Claude Code 的[官方说明](https://code.claude.com/docs/en/how-claude-code-works)也介绍了类似的工作方式：每次工具调用带来的新信息，都会影响下一步的选择。Anthropic 在[工具开发文章](https://www.anthropic.com/research/writing-tools-for-agents)中，则直接用交替调用模型和工具的 `while` 循环来描述简单的 Agent loop。

拾事中的过程可以画成下面这样：

![补充事项依据的工具循环：围绕已有事项，模型选择查询工具，SS 执行并回传结果，最后保存相关发现](images/agent-loop.png)

*以补充事项依据为例，同一次请求可以包含多轮模型与工具调用。图中省略了具体协议和错误处理。*

用简化的伪代码表示，就是：

```text
当前上下文 = 已生成事项 + 相关资料 + 可用工具

while 未取消，且还有时间和预算:
    回复 = 调用模型(当前上下文, 可用工具)

    if 回复包含最终结果:
        校验并保存事项与补充依据
        break

    调用 = 校验工具名和参数(回复)
    工具结果 = SS执行工具(调用)
    当前上下文 += 本次调用和工具结果
```

还是前面的例子。模型围绕已有事项，可能先查询一条相关记录；如果结果里出现了需要核对的配置，再调用配置查询工具。拿到两次结果以后，它可以整理当前发现，也可以继续补查缺少的信息。

这里的查询顺序由模型根据当前信息决定。程序提供可用工具和执行约束，模型选择下一步。没有必要调用工具时，也可以直接返回结果。

模型负责判断，拾事负责把动作做出来。工具返回的实际输出会进入下一轮输入，模型才能据此继续分析。它在回答里写一句“建议查一下配置”，还没有完成这次查询。

在这个场景里，循环的结果是补充后的事项及其依据。同一套工具能力也可以复用在事项分析、生成、修改和归档等业务请求中，最终仍按各自的结果格式返回，沿用当前用途配置的模型，不需要另设一个独立的“工具模型”。

这种可以根据观察结果继续选择动作的过程，让拾事有了一个简单 Agent 的形态。

## 为什么选择通用 CMD 工具

另一个来自 Claude Code 的启发，是尽量复用命令行工具。我把这个取舍概括成“CLI Is All You Need”：一个动作如果已经能通过命令完成，就可以把它包装成工具，接进循环里。

在 Windows 上，我选择了通用 CMD 命令模板。工具可以是一个可执行程序、一段脚本，也可以是调用已有 CLI 的包装命令。查询数据库、读取配置的具体方式，都留在工具内部处理，拾事只负责按约定传参、执行和接收结果。

例如，一个示例工具的命令模板可以写成：

```text
python query_record.py --id {{record_id}}
```

这里的脚本只是说明接口形式，需要用户自行准备。注册时填写工具名、用途、命令模板和参数说明。模型选择这个工具并给出 `record_id` 后，拾事从本地注册信息中取出模板，校验参数，再执行命令。

这样，模型不用生成一整条命令，也不能用回复替换已注册的模板。它看到的是工具能做什么、需要什么参数，实际执行方式由用户配置。

我选择这种形式，主要就是因为简单。已有的脚本和程序可以继续用，也不用为了接入拾事，先给每个查询另做一套专用服务。运行环境、依赖和访问方式由工具自己准备，拾事不需要理解每个业务系统。

固定的查询方式和结果整理，也可以提前封装在工具里。模型按用途选择工具、填入参数，就能取得后续判断所需的信息。这也符合我最初的想法：把这个领域里经常用到的小动作准备好，让模型直接使用。

参数也尽量保持简单，统一按字符串传入。某个值应该解析成数字、日期还是其他业务类型，由工具处理。标准输出和标准错误使用 UTF-8，工具可以直接返回普通文本，拾事再把输出、退出码和执行状态整理后交给模型。

这个选择也有代价：工具作者需要准备好命令运行环境，复杂业务参数需要自己校验，CMD 的引用和转义也有明确限制。目前无法可靠传入的参数会在执行前被拒绝。作为拾事第一版通用工具接口，我更愿意先把这个约定做清楚。

## 不同模型后端，使用同一套工具调度

拾事可以接入 API、Codex 和 DSH。工具配置好以后，我希望换一个模型后端，还能继续使用同一套工具。

因此，在非一键处置的业务请求里，执行权统一放在拾事。不同后端只需要把“想调用什么工具、参数是什么”传回来，协议上的差异由适配层处理。

| 接入方式 | 模型怎样提交工具请求 | 谁执行工具 |
| --- | --- | --- |
| 兼容 API | 原生结构化工具调用 | 拾事 |
| Codex | 按约定返回结构化文本 | 拾事 |
| DSH | 按约定返回结构化文本 | 拾事 |

API 的工具调用本身就能表达工具名和参数。Codex、DSH 的非处置请求，则被当作普通模型后端使用：模型返回一次工具请求，或者返回最终业务结果，适配层把工具请求接入共同的循环。

工具执行之后，真实结果会回到同一个业务请求里，继续使用当前用途配置的模型。上下文补查、图片读取和注册的业务工具，也由拾事统一调度。

这样，只有 API 接入时，也能完成“模型选择工具、SS 执行、结果回传、继续判断”的过程。工具不再依赖某个外部 Agent 客户端是否提供命令执行能力。

到一键处置阶段，Codex、DSH 则作为完整的 Agent 接手调查和解决问题。它们还可以通过原有 MCP 接口中的通用 `ss_tool` 入口，使用拾事已注册的工具，命令执行和调用记录继续共用实现。

## 循环简单，执行过程仍然要管住

循环本身不长，真正落到程序里，还需要处理执行过程中发生的变化。

首先，模型只能选择本次提供的工具。用户在本地注册、启用工具，才会把它交给模型使用。消息和工具输出都作为资料进入上下文，不能靠其中一句话新增工具、打开开关或扩大权限。

一次请求使用冻结的工具目录，让模型看到的说明和实际执行映射保持一致。不过，在每次命令启动前，拾事还会检查工具是否仍然启用。如果用户已经关闭工具，后续调用就不能继续启动。

其次，整个循环共用总时限、取消状态和输入预算。多调用一次工具，不能重新获得一份完整的执行时间；输出太长，也不能无限追加到下一轮。取消或超时后，拾事会回收本次拥有的子进程。

还有一个容易忽略的问题：命令执行和结果保存是两个动作。命令可能已经运行，模型请求却失败了，或者执行结果没有成功保存。此时直接从头重来，可能把已经做过的操作再做一遍。

所以拾事会先持久保存调用意图，再启动命令，执行后保存结果。相同调用编号不会重放；遇到网络失败或结果未知，也不会自动重新执行。这不能消除所有不确定性，但能把“尚未执行”和“可能已经执行”区分开来。

每次调用都会留下工具名、参数、用途、状态、退出码和有界输出。批量分析涉及多个事项时，调用按实际使用关系关联到具体事项，避免把整批查询都挂到每一条事项上。

这些记录也方便我回头核对：这条事项参考了哪次查询，工具实际返回了什么，模型的判断有没有超出已有信息。

## 从用户操作中积累经验

工具补充的是当前事实，记忆保存的是后续还可能用得上的经验。

上一篇里，归档记忆的写入依据主要是明确填写的归档备注。这一轮，我把来源扩展到了本批操作记录：事项修改、状态调整、合并、撤销和处理结果，都可以成为归纳经验的依据，备注继续补充原因。

用户的反馈不总是写成一句规则。修改一条事项、合并两个重复事项，或者纠正一次状态判断，本身就能提供一些信息。如果每次都必须再写一段备注，很多反馈就很难留下来。

不过，操作发生了，并不意味着原因也明确。一条事项被标为“无需处理”，可能是已经在线下解决，也可能只是这次临时不用管。单凭这个动作，不能直接推导出“以后这类消息都不用生成事项”。

归档需要结合本批记录判断哪些经验可以复用，优先参考人工纠正和明确说明。每项记忆变更都要引用本批有效来源，证据不足时保留原记忆，一次性例外也不推广成长期偏好。程序可以检查来源和写入范围，具体归纳是否合理，仍然需要能够查看和修正。

这里积累的是用户私有的上下文。消息分析维护临时记忆，归档维护归档记忆，用户可以查看和编辑。提示词、规则和标签的采用仍由用户决定，记忆不会自动把自己变成新的系统指令。

后续分析仍然要以当次资料为依据。旧经验可以帮助理解问题，当前工具查到的数据也可能推翻之前的判断。产生冲突时，就需要继续核对。
